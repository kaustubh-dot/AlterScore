# AlterScore Website QA Report - 2026-07-02

## Scope

Tested the AlterScore React/Vite frontend and FastAPI scoring backend locally.

- Desktop browser: `1440x900`
- Mobile browser: `390x844`
- Tablet/mobile breakpoint check: `768x1024`
- Scoring QA: 50 varied in-process scoring cases via checked-in runtime bundle, plus live API/manual script checks
- Verification commands: `npm.cmd run lint`, `npm.cmd run build`, `GET /api/health`

Screenshots captured under `.logs/qa-screens/`.

## Verification Summary

- Backend health passed: runtime model loaded, manifest-backed, promotion gate passed.
- Frontend lint passed.
- Frontend build passed, but emitted a large chunk warning: `dist/assets/index-*.js` is `732.93 kB`, `224.75 kB gzip`.
- Live desktop assessment could be completed through the browser and eventually produced results.
- Live mobile landing, assessment, modal, results, and tablet dashboard surfaces were checked.
- The checked-in `scripts/manual_test_payloads.py` failed immediately with HTTP 422.

## High-Priority Findings

### 1. Results content can remain invisible on desktop

Severity: Blocker / serious UX bug

Evidence:
- Live desktop result page reached `/results`, but multiple sections stayed at `opacity: 0`.
- DOM text existed for SHAP, optimizer, counterfactuals, tips, and actions, but panels were visually hidden.
- Full-page screenshot repeated the visible score/header area and showed large blank vertical regions.

Likely cause:
- `Results.jsx` depends on `playSuccess` in the reveal effect dependency array.
- `useSound()` returns fresh function identities each render, so timers can reset before `animationStep >= 4` settles.

References:
- `frontend/src/pages/Results.jsx:88`
- `frontend/src/pages/Results.jsx:175`
- `frontend/src/pages/Results.jsx:188`
- `frontend/src/pages/Results.jsx:307`
- `frontend/src/pages/Results.jsx:336`
- `frontend/src/pages/Results.jsx:373`
- `frontend/src/pages/Results.jsx:460`
- `frontend/src/pages/Results.jsx:483`
- `frontend/src/pages/Results.jsx:504`

Suggested fix:
- Memoize functions returned by `useSound()` with `useCallback`, or remove unstable sound callbacks from animation effect dependencies using a stable ref.
- Add a regression test that waits for result sections to become visible.

### 2. Assessment-to-results transition is too slow and has no progress honesty

Severity: Serious

Evidence:
- Live desktop flow stayed on the completed processing screen for about 90 seconds before navigating.
- Processing showed all steps completed and no error, but continued to say "Please wait".

References:
- `frontend/src/pages/Processing.jsx:45`
- `frontend/src/pages/Processing.jsx:46`
- `frontend/src/pages/Processing.jsx:47`

Suggested fix:
- Add a real pending state after animation completes, plus elapsed-time feedback.
- Add timeout/retry handling and backend latency instrumentation.
- Consider moving expensive explanation/counterfactual generation behind a staged response if scoring remains slow.

### 3. Main frontend bundle is too large for mobile first load

Severity: Serious

Evidence:
- `npm.cmd run build` passed but warned that the main JS chunk is larger than 500 kB.
- Current output: `732.93 kB`, `224.75 kB gzip`.
- Mobile users load dashboard/admin/Recharts code before using those routes.

References:
- `frontend/src/App.jsx:8`
- `frontend/src/App.jsx:18`
- `frontend/src/App.jsx:92`
- `frontend/src/App.jsx:93`

Suggested fix:
- Route-split `Dashboard`, `Admin`, `Results`, and other heavy views with `React.lazy` and `Suspense`.
- Split Recharts-backed dashboard chunks.

### 4. Scoring calibration/spread is softer than product expectations

Severity: Serious

50-case scoring QA summary:
- 40/40 valid cases scored without crashes.
- 10/10 invalid cases were rejected by schema validation.
- All scores stayed within `300-850`.
- All probabilities and percentiles stayed bounded.
- Risk band and loan eligibility were internally consistent in the scoring service.

Concerns:
- No tested valid profile reached `excellent`; valid cases ranged `300-746`.
- Golden profile expectations appear stale: examples expected `840-850/excellent` but scored around `698/good`.
- Counterfactual actions were empty in 5/40 valid cases.
- Severe telemetry-abuse cases can still remain high: bot-fast profile scored `706/good`; erratic low-engagement scored `651/good`.
- Scenario and text signal spread looks compressed.

Suggested fix:
- Refresh golden profile fixtures or codify new expected ranges.
- Decide whether hand-crafted excellent profiles should be reachable.
- Strengthen governance penalties for stacked telemetry abuse if bot-like behavior should not remain `good`.
- Add fallback improvement actions when DiCE returns no counterfactuals.

## Mobile / Responsive Findings

### 6. Tablet dashboard uses an icon-only 60px sidebar

Severity: Serious

Evidence:
- At `768x1024`, `/dashboard` renders a fixed `60px` left rail with hidden labels.
- Content is squeezed by the rail on a touch-size viewport.

References:
- `frontend/src/pages/Dashboard.css:86`
- `frontend/src/pages/Dashboard.css:367`
- `frontend/src/pages/Dashboard.css:372`

Suggested fix:
- Use bottom navigation up to at least `640px` or `767px`.
- Keep touch targets >= 44px and expose labels on tablet/mobile.

### 7. Mobile numeric question autofocus opens keyboard immediately

Severity: Medium

Evidence:
- On `390x844`, after entering assessment, `document.activeElement` is `INPUT.input-number`.
- This opens the mobile keyboard and compresses the first-question layout.

Reference:
- `frontend/src/pages/Assessment.jsx:438`

Suggested fix:
- Disable autofocus on coarse pointers or only focus after explicit user intent.

### 8. Modal layering conflicts with assessment chrome

## Accessibility / Interaction Findings

### 10. Scenario and Likert selections lack accessible state

Severity: Serious

Evidence:
- Selected state is class-only: `selected`, `primary-selected`, `least-selected`.
- Scenario buttons expose repeated accessible names: `Most`, `Least`.
- Likert accessible text is effectively `3 NEUTRAL`, which broke exact label targeting and can be noisy for assistive tech.

References:
- `frontend/src/pages/Assessment.jsx:452`
- `frontend/src/pages/Assessment.jsx:470`
- `frontend/src/pages/Assessment.jsx:491`
- `frontend/src/pages/Assessment.jsx:497`
- `frontend/src/pages/Assessment.jsx:500`
- `frontend/src/pages/Assessment.jsx:504`
- `frontend/src/pages/Assessment.jsx:507`

Suggested fix:
- Use radio/radiogroup semantics or `aria-pressed`.
- Add option-specific labels such as `Most like me: ${opt.text}` and `Least like me: ${opt.text}`.

### 11. Ambient audio starts by default after first interaction

Severity: Serious UX/accessibility issue

Evidence:
- `App.jsx` calls `initAudio()` on first click, keydown, or touchstart.
- `useSound` defaults muted only if `localStorage.alterscore_sound_muted === 'true'`; otherwise audio can start by default.

References:
- `frontend/src/App.jsx:25`
- `frontend/src/App.jsx:47`
- `frontend/src/App.jsx:62`
- `frontend/src/hooks/useSound.js:367`

Suggested fix:
- Default to muted and require explicit opt-in from the sound button.

### 12. Reduced-motion users still receive blocking JS animations

Severity: Serious accessibility issue

Evidence:
- Preloader runs a 2.5s `requestAnimationFrame` sequence.
- Results reveal uses multiple timeouts and a score count-up animation.

References:
- `frontend/src/components/ui/Preloader.jsx:15`

### 13. Custom cursor removes native input cursor affordance

Severity: Medium

Evidence:
- Custom cursor CSS applies `cursor: none !important` to inputs and textareas.

Reference:
- `frontend/src/components/ui/CustomCursor.css:83`
- `frontend/src/components/ui/CustomCursor.css:85`

## Visual Notes

What works:
- Mobile landing at `390px` has no horizontal overflow and the primary CTA remains reachable.
- Mobile assessment controls are large enough and stack predictably.
- Mobile results sections are visible because CSS forces mobile fade-in content to opacity `1`.

What lags:
- Desktop results reveal is unreliable.
- Full-page result screenshots expose repeated fixed/chrome artifacts and hidden content.
- The visual style is dramatic but sometimes fights utility: dashboard/tablet nav and assessment accessibility need more product-tool discipline.

## Recommended Fix Order

1. Fix `Results.jsx` reveal instability and add a browser regression for visible result sections.
2. Fix processing latency/feedback and capture scoring endpoint timing.
3. Route-split heavy frontend views.
4. Update `scripts/manual_test_payloads.py` and golden scoring expectations.
5. Improve assessment semantics for MCQ/Likert/scenario controls.
6. Change audio to explicit opt-in and respect reduced motion in preloader/results.
7. Fix dashboard tablet navigation and modal z-index.
8. Review scoring governance penalties and counterfactual fallback behavior.
